# AniMusicCollector

每季度把当季新番的 OP/ED 整理出来，收进网易云音乐的季度歌单。

你只做四步：**拉番单 → 收曲目 → 确认匹配 → 推送**。其余的事（读 Bangumi 在看列表、
从日文维基/AnimeThemes 取主题歌、去网易云搜候选、打分排序、写歌单）程序都替你做了。

---

## 一、第一次打开：先选两个程序路径

「环境」那两行的路径**默认是空的**（安装位置每台机器都不一样，程序不去猜）。
点各自那行的 **「浏览…」** 各选一次：

| 那行 | 选什么 |
|---|---|
| 浏览器 | **Chromium 内核**的浏览器 exe：Chrome / Edge / Brave / Vivaldi / Chromium…<br>**Firefox / Safari 不行**（它们的远程调试不是 CDP，程序读不到数据） |
| 网易云客户端 | `cloudmusic.exe`（网易云音乐 PC 客户端） |

选完会**自动记住**，下次不用再选。两行右边的状态灯告诉你连上没有：

- `未启动` —— 还没启动，或端口不对
- `已连接 (154.0.x)` —— 连上了
- 浏览器那行还会显示 `已连接 · 已登录` / `已连接 · 未登录` —— **未登录就读不到你的在看列表**

> 浏览器那行下面还有一行 **profile**（浏览器的「用户数据目录」，bgm.tv 的登录态就在里面）。
> 它按所选浏览器自动生成，也可以自己改；**鼠标悬停最右边的 ⓘ** 有完整说明。

## 二、四步操作流程

```
① 番单            ② 曲目              ③ 匹配                ④ 推送
从 Bangumi       拉 OP/ED           去网易云搜 + 打分       写进歌单
拉「在看」   →   勾掉不收的     →   人工确认拿不准的   →   试运行 → 推送
```

界面顶部是**季度选择**与**目标歌单名**；中间是当前步骤；底部是**日志面板**
（每一步做了什么、每个数字什么意思都写在那里 —— 见第三节）。
右下角是 `← 上一步` / `确认并下一步 →`。

### ① 番单：从 Bangumi 拉「在看」

| 按钮 | 用途 |
|---|---|
| **从 Bangumi 拉取「在看」** | 读取你在 Bangumi 标记为「在看」的动画，按当前季度筛选后入库 |
| 仅从 AnimeThemes 拉当季 | 不用 Bangumi：**有意地**把 AnimeThemes 的**当季全部**番收进来（想"先把整季收进来再挑"时用） |
| 增量重跑（周更） | 只处理新的和值得重试的（见第四节） |
| 排除补充的番 | 上一条带进来一堆没在看的番时，一键把它们**取消纳入**（不删数据） |

拉完以后你会看到一列番剧，**「纳入」那个勾就是要不要参与后续流程**：

- 不想收集的番 → **取消勾选**（右键也有「从结果中排除」）；第②步会跟着把它那些曲目
  一起标成"已排除"，第③步起就不出现
- 番名不对 → 直接双击单元格改（中文名 / 日文原名 / 首播日都能改）
- Bangumi 漏标的番 → **「+ 新增番剧」**手工补一行
- 点了「仅从 AnimeThemes 拉当季」之后番单里多了几十部 → 点 **「排除补充的番」**收尾
  （判据是"来自 AnimeThemes 且没和 Bangumi 对上号"的番；**只改纳入、不删除**，
  曲目/候选/匹配决策全留着，勾回来就恢复；手工新增的番不受影响）

### ② 曲目：拉取 OP/ED、挑要收录的

| 按钮 | 用途 |
|---|---|
| **拉取 / 更新 OP/ED** | 给**第①步勾选的番**重新取一次主题歌（日文维基优先，AnimeThemes 回退）。<br>**只碰这些番，不会把当季全部番拉进来** |
| 全选 / 反选 | 只作用于**当前看得见**的行（配合筛选用） |
| 查看未收录的番 | 哪些番两个数据源都没有主题歌 —— 需要你手工补 |
| + 新增曲目 | 手工补一条（例如数据源漏了） |

**第①步管"哪些番"，第②步管"哪些曲"** —— 进入这一步时日志会打一行现在的情况：

```
→ 步骤 2：ThemePage
    第②步只管「哪些曲」：共 15 条 · 收录 12 条 · 已排除 3 条（其中 2 条是因为它的番在第①步被排除了）· 手工补充 1 条
    这里取消「收录」的曲目不会进入匹配与推送；手工改过的行重跑拉取不会被覆盖。
```

「收录」那个勾 = 这首要不要进后面的匹配与推送，**默认全勾**。你只要取消不想要的
（比如只收 OP 不收 ED，或者某个版本的曲子不想要）。

筛选框里有 `全部 / 仅 OP / 仅 ED / 已排除 / 手工补充` —— 想确认"我排除了什么"就切到「已排除」。
⚠️ 如果某条显示已排除、而它属于第①步被排除的番，**在这里打勾是没用的**（番没纳入，
曲目也不会参与）—— 要回第①步把那部番勾回来。

每行都能改：「类型」可切 OP/ED、曲名/艺人/序号都能双击改。
**手工改过的行会标记「手工」，之后重跑拉取不会覆盖它**（只填空白字段，也不会把你的勾选改回去）。

### ③ 匹配：去网易云搜，然后人工确认

点 **「开始匹配网易云」**。程序对每条曲目去网易云搜索、打分（曲名 / 艺人 / 番剧标注 / 时长），
给出候选，并按置信度分成三类：

| 标记 | 含义 | 你要做什么 |
|---|---|---|
| 🟢 `自动通过` | 分数够高（默认 ≥0.80） | 一般不用管，可以直接进第④步 |
| 🟡 `待审核` | 有点拿不准 | **需要你看一眼**：左边点候选、或粘贴链接手动指定 |
| ⬜ `未上架` | 网易云还没有这首歌 | 等（周更会自动捡回来），或手动指定 |
| 🔴 `未收录` | 数据源（维基/AnimeThemes）都没有这条主题歌 | 手工补曲目，或手动指定网易云 ID |

界面分两栏：**上面是曲目表**（一行一条目标曲目），**下面是这一行的候选卡片**
（每张卡片一首网易云歌曲，点卡片选中，`试听` 可以在浏览器里打开）。

拿不准时你有这些选择：

| 操作 | 作用 |
|---|---|
| 点候选卡片 / **「手动指定」** | 选用这首（粘贴网易云链接或歌曲 ID 也行） |
| **「都不是，跳过此曲」** | 候选里没有对的 → 记为「已跳过」，它不会进第④步，也不算"待处理" |
| **「↶ 撤销」/ `Ctrl+Z`** | 退回上一次改动（误点候选、批量采用都能退） |
| 右键 → **清除此行的匹配** | 把这一行退回「待审核」，重选 |
| **「全部采用自动结果」** | 一次把所有自动结果确认掉（之后还能用 `↶ 撤销` 退回来） |
| **「只看待审核」/「显示全部」** | 快速跳到需要你处理的那些行 |

**你的确认会变成"经验"**：确认过的对应关系会写进别名表，下次同样的曲目直接自动通过
（实测自动通过率 23.7% → 49.9%）。

### ④ 推送：写进歌单

| 按钮 | 用途 |
|---|---|
| **试运行** | 只列出"会推什么"，**不碰账号、不写入**（没装客户端也能用） |
| **检查目标歌单** | 看目标歌单在网易云里存在吗、里面已有什么 |
| **推送到歌单** | 真正写入（**这是唯一会改动你账号的动作**，会先弹确认框） |

推送前请确认：

- 顶部的**目标歌单名**（默认按季度生成，例如 `26年10月`；不存在会自动创建）
- 每行的**「推送」勾选** —— **只推勾选的**（取消勾选 = 这次不推，不会记为"永久跳过"）
- 每行的**「目标歌单」**列 —— 可以逐行改成别的歌单，一次推送就能分发到多个歌单

> ⚠️ **首次真机推送建议只推一首**（勾掉其余）。程序对每首歌都**回查确认**：
> 读不到才算成功、绝不假装成功。已经推过的歌会被识别出来（幂等），重复推送不会重复加。

## 三、日志怎么看

日志面板是底部那块。**看不懂某一行时先来这里对照。**

### 启动那几行（每次启动都打）

```
AniMusicCollector 启动 · 季度 2026Q4（2026 秋） · 目标歌单「26年10月」
  数据库 D:\...\data\state.db
  配置 ...\config · 报告 ...\reports · 程序根目录 ...（打包运行：是）
  进程令牌 完整性=中 受限=否 AppContainer=否 管理员=否
  环境 TEMP=... · LOCALAPPDATA=... · __COMPAT_LAYER=（无）
    程序数据目录 可写
    浏览器 profile 可写
    网易云数据目录 可写
```

| 行 | 意思 |
|---|---|
| 数据库 / 配置 / 报告 / 程序根目录 | **程序到底在用哪个库、哪份配置** |
| 进程令牌 | 正常必须是 `完整性=中 受限=否`。显示**低**说明程序被降级运行了（见第五节） |
| 三个「可写 / 不可写」 | 外部程序（浏览器、网易云）要写的地方。**不可写**就是第五节那个坑 |

### 拉取番单（第①步）

```
读取 Bangumi「在看」列表…
  路径=api_tab，共 87 条
  属于 2026Q4 的 5 条
拉取 AnimeThemes 当季番单（只用于匹配名字与回退曲目，不会加入番单）…
  当季 49 部（匹配池）
  AnimeThemes 名称匹配上 3/5 部（池子里另外 46 部与你在看的番无关，不会入库）
  其中 5 部的曲目来自维基百科
完成：5/5 部拿到曲目（维基 5 部）
本步用时 26.4 秒 · HTTP 请求 21 次（维基 6 · AnimeThemes 13 · AniList 2）· 缓存命中 0 次
  网络往返合计 18.1 秒 · 限速等待 6.0 秒 · 最慢一次 2.1s ja.wikipedia.org/w/api.php?action=query&prop=revisions&titles=…
  维基调用 6 次（批量，每次 ≤12 个候选名）→ 网络请求 6 次（重试 0 · 限流重试 0 · 缓存命中 0）
      候选名 60 个 = 命中缓存 0 + 查无此词条 51 + 取到正文 6 + 没问到 3（没问到的是**我们没问到**，不是「维基没有」） · 取到正文但没主题歌栏 0 · 搜索兜底 1
```

| 数字 | 口径 |
|---|---|
| `共 87 条` | 你在 Bangumi 标「在看」的**全部**动画（不分季度） |
| `属于 2026Q4 的 5 条` | 上面那些里落在当前季度的 —— **这 5 条才是你的番单** |
| `当季 49 部（匹配池）` | AnimeThemes 上这一季的全部番，**只用来帮你的番匹配名字**（以及维基没有时回退曲目）。<br>**不会**变成你的番单 —— 看到 49 别慌 |
| `匹配上 3/5` | 5 部在看番里，有 3 部能在 AnimeThemes 池里对上名字。**没对上不代表没有曲目**：维基凭日文名也能直接拿到 |
| `完成：5/5 部拿到曲目` | 真正有曲目进库的番数 / 番单总数 |

**`本步用时` 那几行 = 「时间到底花在哪」**，专门用来判断慢在哪：

| 词 | 意思 |
|---|---|
| `HTTP 请求 59 次（维基 44 · AnimeThemes 13 · AniList 2）` | **真的发出去了多少次网络请求**（重试各算一次）。按源分开数，因为三个源走的出口不一样（维基在大陆必须过代理） |
| `缓存命中 3 次` | 命中本地缓存、**一次网络都没发**。同一天重跑基本全命中，所以第二次总是快得多 |
| `慢请求 ≥3s N 次` | 单次请求超过 3 秒的次数。**基本就是网络/梯子的问题**（维基正常都在 1 秒内），不是请求太多 |
| `失败 N 次（重试 N 次）` | 重试到用完仍然失败的请求数。后面会逐条列出失败的 URL 和原因 |
| `按服务端要求等待 X 秒（429）` | 被限流后**服务端明确要求**等的时间（它会在响应头里写 `Retry-After: 25`）。与下一项分开记，否则分不清「谁在吃时间」 |
| `网络往返合计` | 所有请求真的在网络上花掉的时间之和 |
| `限速等待` | **我们自己规定**要等的时间（维基 1 请求/秒）。它大不等于网络慢 |
| `退避等待` | 重试之间**我们主动等**的时间。它大 = 有请求在失败 |
| `最慢一次` | 最慢的那一条请求及其地址 —— 卡住的时候就是它 |
| `维基调用 6 次（批量，每次 ≤12 个候选名）→ 网络请求 6 次（重试 0 · 限流重试 0 · 缓存命中 0）` | **可以逐项对账**：`网络请求 = 调用 − 缓存命中 − 熔断跳过 + 重试 + 限流重试`。<br>「调用」是**批量请求**的次数（一次问一整套候选名），差值要么是缓存命中（好事）、要么是重试/限流重试（坏事）、要么是熔断后主动跳过 |
| `候选名 60 个 = 命中缓存 0 + 查无此词条 51 + 取到正文 6 + 没问到 3` | 也能逐项对账。`候选名` 是我们**试过的名字个数**（含命中缓存的），一次批量请求可以覆盖十来个名字 |
| `查无此词条 51` | 维基**真的没有**这个词条。数量大说明这部番的日文名不好找 |
| `没问到 3` | **我们没问到**（断网/超时/被限流）—— 和「查无此词条」是两回事，别混。**这一项不为 0 时，覆盖率数字是不可信的** |
| `请求失败 N 次` | 请求级的失败次数（一个批量请求失败会让它 +1，但它覆盖的那些候选名全进「没问到」） |
| `最近一次失败：HTTP 429` | 失败的状态码。`429` = 被维基**限流**了（见第五节） |
| `被限流（HTTP 429）N 次` | 收到 429 的次数。后面会写清「其中几次请求被熔断拦下（没发出去）」 |

> 上面这几项相加 ≈ `本步用时`，剩下的就是本地处理（正常很小）。
> 如果某项很大，那它就是你要处理的那个原因。


### 匹配（第③步）

```
待匹配 14 / 共 14 条 theme
    ✓ 紅蓮華 提前终止（0.96 via title+artist）
完成：自动 9 · 待审核 3 · 未收录 1 · 未上架 1
```

| 词 | 意思 |
|---|---|
| `自动 9` | 分数够高，可以直接用 |
| `待审核 3` | 需要你看一眼 |
| `未收录 1` | 数据源里就没有这条主题歌 |
| `未上架 1` | 网易云还没有 —— 等，或手动指定 |
| `提前终止（0.96 via …）` | 分数已经足够高，不用再试其它查询词了（`via` 说明靠什么判断的） |

⚠️ **`搜索失败` 和 `未上架` 是两件事**：搜索失败是**我们没问到**（网络/接口问题），
程序**不会**把它记成"没有这首歌" —— 日志会明确写「不记录结果」，重跑一次即可。

### 推送（第④步）

```
将把勾选的 12 首歌推送到 1 个歌单（未写入）
  歌单「26年10月」12 首
    · 紅蓮華 — LiSA
✅ 推送完成：新增 11 · 已存在 1 · 失败 0
```

| 词 | 意思 |
|---|---|
| `未写入` | 这是**试运行** |
| `已存在 1` | 这首歌之前就在歌单里了（幂等，不会重复加） |
| `失败 0` | 回查确认没读到才叫失败 —— 失败的行会写明原因，重推即可 |

### 操作反馈

你每点一下，日志都会回一行，例如：

```
全部收录：当前显示 14 行（当前筛选「全部」只看得到 14 / 14 行）
筛选「仅 OP」：显示 7 / 14 行
已采用 9 条自动结果（全量）
↶ 撤销「采用候选 · 紅蓮華」：曲名恢复 → …
新增第 15 行 —— 请填写中文名（手工数据不会被重跑覆盖）
```

「当前显示 N 行」是**批量操作**（全选/反选/筛选）的提示：
**筛选只影响显示，不会改变数据** —— 隐藏起来的行照样会被保存和推送
（除非你取消它们的勾选）。

## 四、简单流程之外的功能

### 撤回 / 纠错（第③步）

三条退路，随时可用：

| 操作 | 什么时候用 |
|---|---|
| `↶ 撤销` / `Ctrl+Z` | 刚点错了（误点候选、批量采用）。按钮的 tooltip 会写清"这一次会退掉什么" |
| 右键 → `清除此行的匹配` | 这一行选错了，想退回「待审核」重选 |
| `都不是，跳过此曲` | 候选确实没有对的 —— 记为「已跳过」，不进第④步也不占"待处理" |

> ⚠️ 撤销**退不回已经写进别名表的经验**：如果那次错误选择已经被保存过，
> 别名表里那条对应关系仍在（日志会如实提醒）。要清掉得手工编辑 `config/aliases.yaml`。

### 筛选

每一步右上角都有筛选框，**它只影响显示**（"只看 OP"、"仅自动"、"已排除"…），
数据一行都不会少 —— 保存和推送读的永远是全量。第③步还有
`只看待审核` / `显示全部` 两个快捷按钮。

### 批量勾选 / 右键菜单

- `全选` / `反选` 只作用于**当前看得见的行**（先筛选、再全选，就能批量处理一类）
- 表格里**右键**有：`删除此行`、`从结果中排除（不删除）`、`恢复为数据源值`、`新增一行`
  （第①步还有「纳入/排除」的切换）

> 「排除」和「删除」不一样：**排除**只是不参与（数据留着，随时能恢复）；
> **删除**是真的从库里去掉。

### 换季度 / 补老番

- 顶部的季度下拉框：默认覆盖「今天」前后各一年
- 要选更早/更晚的季度 → 下拉框最后一项 **「其它季度…」**，自己输（例如 `2020Q1`）
- 每个季度的数据是**分开存的**，互不影响

### 增量重跑（周更）

新番歌曲通常**开播后 2~8 周才上架**，所以推荐每周点一次
**「增量重跑（周更）」**：它只处理新的与值得重试的，最后告诉你变了什么：

```
季度 2026Q4 增量重跑结果：新上架 3 · 新匹配 12
  ↻ 重试了 8 条之前搜不到的
  ✨ 新匹配 12 条（auto 9 · pending_review 3）
  ✅ 新上架：theme#42  missing_netease → auto
  库内合计：番剧 12 · 曲目 28 · 候选 940
```

没变化时会明确说「无变化」并解释原因，而不是让你盯着空输出猜。

### 复制命令 / 自己启动外部程序

「环境」那两行右侧的 **「复制命令」** 会把**确切的启动命令行**放进剪贴板，
你可以自己粘到终端里跑：

```powershell
& "C:\Program Files\Google\Chrome\Application\chrome.exe" `
    --user-data-dir=... --remote-debugging-port=9223 --no-first-run https://bgm.tv/
```

> 想换浏览器？直接把那行的路径改成 Edge/Brave 的 exe 即可（profile 会跟着自动换）。
> **注意**：换 profile 目录 = 那个目录里的 bgm.tv 登录态不再使用，需要重新登录一次。

### 导出报告

命令行 `animusic export --season 2026Q4` 会产出：

| 文件 | 内容 |
|---|---|

## 五、常见问题

### 「启动并接管」点了没反应 / 报「路径无效」

1. 路径那行是不是空的？→ 点「浏览…」选一次（见第一节）
2. 文件真的在那个路径吗（可能被卸载/移动了）
3. 端口被占用：把那一行的端口改掉（例如 9223 → 9333），再点启动

### 浏览器起来但状态灯还是「未启动」

- 端口不一样：你手工开的浏览器可能不是程序传的那个端口
- 用「复制命令」自己跑一遍，看有没有报错
- 程序需要**专用 profile**（`--user-data-dir`），Chrome/Edge 136+ 在**默认 profile** 上
  直接拒绝开远程调试 —— 别手动去掉那个参数

### 网易云客户端起来后没有托盘图标、也没有登录态（像全新客户端）

这是 **Windows 完整性级别**问题，不是程序的问题：程序被降级运行了，
它拉起的网易云也跟着被降级，于是**写不了自己的数据目录**。

- **怎么确认**：看启动日志那行 `进程令牌` —— 正常是 `完整性=中`，中招时是 `完整性=低`
- **常见原因**：程序所在文件夹带「低完整性」标签（某些沙箱/安全工具会给工作区加标签）
- **怎么办**：把**整个文件夹**拷到一个普通位置再双击
  （例如 `C:\Users\<你>\Apps\AniMusicCollector\`）。不需要管理员 ——
  以管理员运行只是碰巧绕过了这个限制。程序会在日志里直接告诉你该搬到哪里

### 为什么日志说「当季 49 部」而我的番单只有 5 部？

`49` 是 AnimeThemes 的**匹配池**（用来帮你那 5 部番匹配名字、以及维基没有时回退曲目），
**它不会进你的番单**。你的番单只来自「你在看」∩「当季」。见第三节的口径表。

### 为什么重新拉取要等好几分钟？

程序对每部番要去日文维基找「主題歌」栏，而维基**限速 1 请求/秒**，
一部番可能试好几种词条名（正文 / (アニメ) / (テレビアニメ) / 去掉季数后缀…），
实测一部"找不到"的番就是 6~13 个候选名。**这些名字是一次批量请求问的**
（一次最多 12 个），所以几部番 = 个位数到十几次请求、几十秒。
进度会一行行打在日志里（`第 2/5 部：…`），不会让你干等不知道在干嘛。

**第一步是看 `本步用时` 那几行**（见第三节的口径表），它直接告诉你是哪一种慢：

| 日志里看到 | 是哪种慢 | 怎么办 |
|---|---|---|
| `慢请求 ≥3s N 次` | **网络慢**（梯子） | 换节点，或在 `config/settings.yaml` 把 `fetch.http_timeout` 调小（如 8）让它早点认输 |
| `失败 N 次` 且 `最近一次失败：HTTP 429` | **出口 IP 被维基限流**（不是"没收录"，也不是程序的问题） | 换一个节点（换个出口 IP）再跑；`animusic selfcheck` 能单独确认这一点 |
| `慢请求 0 次 · 失败 0 次`，但 `维基调用` 次数很多、`查无此词条` 占大头 | **请求数**问题（拿注定没有的名字去问） | 梯子再快也没用。现在候选名已改成批量问，如果这一项还是很大，说明这部番的日文名在维基上确实难找 |
| `HTTP 请求` 很少、`缓存命中` 很多 | 正常，缓存生效了 | 不用管 |

想让它快些：

1. **重复拉取有缓存**（维基响应 24 小时；当季番单与 AniList 1 小时 ——
   `fetch.wikipedia_cache_ttl` / `animethemes_cache_ttl` / `anilist_cache_ttl`，
   填 `0` = 不缓存）。同一季度再拉一次几乎瞬时
2. 在第①步把不看的番**取消勾选** —— 第②步的「拉取 / 更新 OP/ED」只处理勾选的番
3. 赛季中想看新增内容，用 **「增量重跑（周更）」**，它只碰有变化的
4. 网络实在差：改 `config/settings.yaml` 里的 `fetch.http_timeout` / `http_retries`
   （默认 15 秒 / 重试 2 次。调小 = 更快放弃，调大 = 更能扛抖动）

### 日志里出现 `HTTP 429 Too Many Requests`

这是**维基百科在限流**，不是你操作错了：429 是服务端说「你（或和你共用这个出口 IP
的其他人）请求太频繁了」。常见的两种原因：

- **梯子节点是共享出口**：同一个 IP 上有很多人在抓维基，配额被别人用掉了。
  **换个节点**通常立刻就好 —— 先用 `animusic selfcheck` 确认（它只发**一个**请求，
  如果连它都报 429，那就是出口 IP 的问题，不是我们的请求太多）。
- 我们自己的请求量偏大：一部番要试 6~13 个候选词条名 —— 现在这些名字是
  **一次批量请求**问的（一次最多 12 个），几部番也就是十几次请求。

**程序现在会按服务端说的办**（服务器会在响应里写 `Retry-After: 25` 这种）：

| 遇到的情况 | 程序做什么 |
|---|---|
| 429 且服务端给了等待时间 | 就等那么久，然后**只重试一次** |
| 429 且没给等待时间 | 等 `5 秒` 再试一次 |
| 同一条请求还是不行 | **放弃这一批候选名**（一次最多 12 个），记成「没问到」—— 不是「维基没有」，也不会退回一个一个重问 |
| **本步为限流等待累计超过 30 秒** | 不再等待，之后遇到 429 直接放弃该请求（防止「成功与 429 交替」时越等越久） |
| **连续** 5 次都被限流 | **熔断**：本步不再向维基发请求，改用 AnimeThemes 回退源，并在日志里明说「是我们被限流了，不是维基没收录」 |

熔断之后日志会长这样 —— 看到它就该换节点或过几分钟重跑：

```
⚠ 维基开始限流（HTTP 429，服务端要求等待 25 秒）—— 停止本步对维基的查询，剩下的番改用 AnimeThemes 回退源
  ⚠ 注意：这不是「维基没收录」，是我们被限流了。换一个节点，或过几分钟重跑即可补齐
…
⚠ 维基曲目源本步被限流中止（HTTP 429，服务端要求等待 25 秒）：有 4 部的曲目来自 AnimeThemes 回退源（罗马音，到网易云的匹配可用率更低）
```

三个阈值都能在 `config/settings.yaml` 的 `fetch` 里调：
`rate_limit_wait_budget`（本步为限流等待的**总预算**，默认 30 秒）、
`rate_limit_retries`（一个 URL 最多重试几次）、
`rate_limit_breaker`（连续几次熔断）。

### 数据会不会被覆盖？

- **手工改过的行不会被覆盖**：标了「手工」的行，之后任何拉取只填空白字段
- **排除 ≠ 删除**：排除只是这次不参与，数据都在
- 想彻底重来：换一个库（见第六节），旧库留着随时能回去

### 端口 9222 / 9223 被别的程序占了

改那一行的端口即可（界面里能直接改）。注意：**界面里改端口只在本次运行有效**
（路径和 profile 会写进配置，端口暂时不会）。

## 六、命令行（不想开界面时用）

图形界面能做的事，命令行都能做（`animusic` = 绿色版里的 `animusic.exe`）。

```powershell
# 环境自检
python -m animusic doctor
python -m animusic selfcheck

# 启动并接管浏览器 / 客户端
python -m animusic launch browser
python -m animusic launch netease

# 四步
python -m animusic fetch  --season 2026Q4      # ① 读在看 + 拉 OP/ED
python -m animusic match  --season 2026Q4      # ③ 搜索 + 打分
python -m animusic push   --season 2026Q4      # ④ 默认试运行，加 --yes 才真写
python -m animusic export --season 2026Q4      # 导出报告

# 周更
python -m animusic update --season 2026Q4

# 只读地看网易云（不写入）
python -m animusic netease health
python -m animusic netease find --name 26年4月
```

| 命令 | 作用 |
|---|---|
| `animusic doctor` | 环境自检（依赖 / 数据源 / 两个 CDP 目标） |
| `animusic selfcheck` | 离线自检（不联网、不碰账号） |
| `animusic launch browser\|netease` | 用正确参数启动并接管（失败时给诊断 + 可复制命令） |
| `animusic bangumi probe\|whoami\|list` | 验证 Bangumi 读取路径 / 查登录 UID / 列在看 |
| `animusic fetch --season 2026Q4` | 读在看列表 + 拉 OP/ED |
| `animusic match --season 2026Q4` | 搜索网易云 + 打分（`--retry-missing` 只重试缺歌） |
| `animusic update --season 2026Q4` | 季度内增量重跑（周更） |
| `animusic push --season 2026Q4` | 推送到歌单（默认试运行，`--yes` 才真写，`--limit 1` 小批量） |
| `animusic export --season 2026Q4` | 产出 CSV / 导入清单 / 缺失清单 |
| `animusic netease health\|playlists\|find\|state` | 网易云客户端只读访问 |
| `animusic aliases show\|learn\|check` | 别名表查看 / 自学习 / 查冲突 |

所有命令都支持全局 `--db <path>`（默认 `data/state.db`），换个库便于试错。

## 七、数据在哪 / 备份 / 换库

```
<程序根目录>/
  data/state.db          ← 你的全部数据（番单、曲目、候选、匹配决策、推送记录）
  config/settings.yaml   ← 本机配置（两个程序路径、端口、阈值…）
  config/aliases.yaml    ← 学出来的别名表
  reports/               ← 导出的报告
  logs/                  ← 启动外部程序时，子进程自己的输出（排查启动失败看这里）
```

- **绿色版（exe）**时 `<程序根目录>` = exe 所在目录。启动日志第 2、3 行会打印实际路径
- **备份**：拷走 `data/` 和 `config/` 就够了（reports/ 能重新导出）
- **换库**：命令行加 `--db 别的路径.db`；想整体换位置就设环境变量 `ANIMUSIC_HOME=<目录>`
- **沿用旧数据**：把旧的 `data/` 与 `config/` 拷到新位置即可（程序不会自己搬你的数据）

## 八、数据来源与许可（署名是义务）

曲目主数据源是**日文维基百科的「主題歌」栏**，正文授权 **CC BY-SA 4.0**。
因此**任何导出物（CSV / 报告 / 歌单清单）都必须带署名，衍生内容也要以同样许可分发**。
导出时程序会自动带上：

```
主題歌データ出典: ウィキペディア（CC BY-SA 4.0）
```

| 产物 | 署名落在哪 |
|---|---|
| `reports/{季度}_match.csv` | 每行带 `source` 列（`wikipedia` / `animethemes` / `manual`…），逐条可追 |
| `reports/{季度}_match_SOURCES.md` | 署名全文 + 逐来源条数 + `source` 取值说明 |
| `reports/{季度}_match_missing.md` | 页脚再写一遍署名（这份最常被单独转发） |
| `reports/{季度}_match_import.txt` | **刻意不加**署名行：多一行会被网易云当成一首找不到的歌 |

其它来源（番单 Bangumi、日文原名 AniList、匹配候选 网易云搜索 API）
请遵守各自站点的条款。
